# Gyro 功能文档

## 1. 项目定位

Gyro 是一个嵌入业务进程的 Go 客户端侧分片中间件。应用提供业务 key，Gyro 返回应访问的后端节点；路由、节点连接、健康状态和服务发现都在本地完成。它不是代理进程、数据复制系统，也不提供集群共识。

Gyro 的一致性哈希算法已拆分为独立依赖 `github.com/focusandinsist/consistent-go/consistent`。Gyro 负责把该算法与服务治理和协议客户端连接起来。

## 2. 功能总览

### 2.1 两级一致性哈希路由

`consistent-go` 先把 key 映射到固定分区，再由分区表映射到成员：

```text
业务 key -> 分区 ID -> 分区 owner -> Gyro Node -> 原生客户端
                         ^
             64 位哈希环和虚拟节点用于计算/调整分区归属
```

默认参数为 271 个分区、每个成员 20 个虚拟节点、负载系数 1.25。成员增加时只检查新虚拟节点影响的区间；成员删除时只重新分配被删除成员负责的分区。分区数反映的是分片管理粒度，不是 key 数量或真实 QPS。

独立库还提供：

- `LocateKey`、`FindPartitionID`、`GetPartitionOwner`；
- `LocateReplicas` 和按分区选择候选成员；
- `LoadDistribution`、`AverageLoad`；
- xxHash64（默认）和 MurmurHash3；
- 公开方法的 `context.Context` 与读写锁保护。

### 2.2 服务发现与动态拓扑

`ServiceDiscovery` 接口提供 `Discover`、`Watch`、`Register`、`Unregister`，调用方可以接入注册中心、Kubernetes Endpoints 或自定义控制面。仓库内的 `StaticServiceDiscovery` 适合固定地址和测试。

`Client.Start` 建立节点 watch，并对节点列表做增量 diff：只创建新增节点、关闭并移除下线节点、重建地址发生变化的节点，不整体重建所有连接。watch 建立失败或意外关闭时使用指数退避重试，最多 10 次，并通过 `Client.Health` 暴露服务发现健康状态和重试信息。

### 2.3 健康检查与故障转移

`DefaultHealthChecker` 支持：

- 可开关的周期检查，默认间隔 30 秒、超时 5 秒；
- 连续失败阈值（默认 3 次）和连续恢复阈值（默认 2 次），减少状态抖动；
- 最多 10 个 worker 的检查池，避免节点数量增长时无限创建 goroutine；
- 节点统计、健康监听器和运行时配置更新。

`HealthAwarePool` 在路由结果为不健康节点时，尝试同 key 的其他候选节点；若候选也都不健康，则返回原始节点，让调用方决定是否失败、降级或重试。这是故障转移提示，不等于 Gyro 已替业务完成重试或数据复制。

### 2.4 协议适配和原生 API

内置适配器包括：

- Redis：基于 `go-redis/v9`，返回原生 `*redis.Client`；
- gRPC：基于 `grpc-go`，返回原生 `*grpc.ClientConn`。健康检查优先使用标准 `grpc.health.v1.Health`，服务未实现该协议时回退到连接状态。

应用可以继续使用底层客户端完整 API，不需要学习 Gyro 自定义命令层。Redis 和 gRPC 都支持按 key 获取主客户端、获取副本客户端以及获取全部客户端。

### 2.5 配置、统计与扩展点

`ClientConfig` 将 Locator、HealthChecker 和 Connection 配置分开管理，支持 watcher 和运行时更新。核心抽象 `Node`、`NodeFactory`、`Locator`、`HealthChecker` 和 `ServiceDiscovery` 均为接口，便于替换协议、注册中心和测试桩。`Client.GetStats`、`HealthAwarePool.GetStats` 和节点健康统计可用于基本运维观测；日志默认丢弃，可通过 `SetLogger` 注入 `slog.Logger`。

## 3. 主要特点和优势

1. **路由稳定且迁移单位明确**：固定分区让扩缩容影响可枚举、可统计，适合缓存预热、分片迁移或任务转移。
2. **有界负载而非只依赖随机均匀**：虚拟节点改善分布，负载系数限制单成员可承载的分区数，降低小规模集群的偶发热点。
3. **读路径短**：查询只需一次 key hash、分区定位和内存表读取，不在每次请求中遍历完整虚拟节点环。
4. **故障处理在客户端完成**：健康探测、阈值防抖和副本候选选择组合在一起，后端节点短暂异常时不必让业务维护一套节点状态缓存。
5. **服务治理与协议解耦**：发现、节点工厂和健康检查可注入；内置 Redis/gRPC 只是适配器，不限制业务使用原生 SDK。
6. **适合 Go 服务生命周期**：公开操作接受 context，成员增删和配置变更返回 error，客户端支持 Start/Stop/Close，便于嵌入 HTTP、gRPC 或后台 worker。

## 4. 适用场景

- Redis、KV 或对象存储的客户端侧分片；
- 多个 gRPC 后端按租户、用户或资源 ID 做稳定路由；
- 需要会话亲和性的服务调用；
- 按租户、任务或消息 key 把有状态工作分配到 worker；
- 节点地址由注册中心或 Kubernetes 动态提供、但请求路由必须保持稳定的云原生服务。

不适合把 Gyro 当作：跨节点事务协调器、数据副本/一致性协议、自动数据搬迁执行器，或需要 TLS 配置开箱即用的 gRPC 客户端（当前 gRPC 连接使用 insecure credentials）。

## 5. 与其他开源实现的比较

下表比较的是工程取舍，不宣称在所有指标上优于其他项目：

| 项目 | 典型模型 | Gyro/consistent-go 的差异化优势 | 对方更适合的情况 |
| --- | --- | --- | --- |
| `groupcache/consistenthash` | 经典虚拟节点环，key 直接落到节点 | 固定分区、负载上限、增量重平衡、健康与服务发现整合 | 只需要极小的经典哈希环 |
| `stathat/consistent` | 经典环，Add/Remove/Get/GetN | 可枚举分区、分区负载观测、明确的候选副本接口 | 偏好成熟且简单的传统环 API |
| `serialx/hashring` | 哈希环并支持节点权重 | 两级分区模型、固定迁移单位、健康感知路由 | 异构节点权重是首要需求 |
| `buraksezer/consistent` | 固定分区的有界负载一致性哈希 | Gyro 额外提供服务发现、健康阈值、Redis/gRPC 原生客户端；consistent-go 的成员 API 使用字符串并支持 context | 更看重上游生态、成熟度和既有行为契约 |
| `dgryski/go-jump` | Jump Consistent Hash，连续 bucket | 支持任意字符串成员、成员删除、候选副本和可观察分区表 | bucket 可连续编号且追求极简 O(1) 内存 |

综合优势在于组合，而不是单项算法宣传：Gyro 把“稳定路由 + 有界分区负载 + 增量拓扑更新 + 健康摘除 + 原生协议客户端”放在一个可注入的进程内组件中。

## 6. 当前边界与可优化之处

以下是从当前代码直接确认、且有实际收益的事项；除此之外没有必要为了增加路线图而强行列优化：

1. **gRPC 安全配置**：适配器固定使用 insecure transport，生产环境若需要 TLS/mTLS 需要扩展连接配置和凭证注入。
2. **健康检查锁粒度**：`DefaultHealthChecker.Check` 在持有内部互斥锁时调用节点网络健康检查，网络慢时会阻塞其他健康状态读写；可改为锁外执行探测、锁内提交结果。
3. **连接配置热更新**：连接配置变化目前只记录 warning，不重建已有节点连接；如果需要运行时调整连接池或超时，应实现节点平滑重建。
4. **一致性库状态原子性**：`consistent-go` 的 `Remove` 在重分配中途容量不足时可能已经修改部分状态；应采用临时状态验证后一次提交，或完整回滚，并补充回归测试。
5. **一致性库成员缓存**：`GetMembers` 首次构建缓存时的 `copy` 目标长度为 0，后续读取可能返回空列表；应修复缓存复制并测试连续读取。

这些项目属于正确性、发布和可运维性改进。权重路由、数据迁移执行器、跨进程快照或 gossip 等能力是否加入，取决于产品定位，不是当前核心功能的必需优化。

## 7. 使用约束

- 所有客户端进程必须使用相同的成员 ID、哈希函数、分区数、复制因子和负载系数。
- 修改哈希函数或分区数会大范围改变 key 映射，应按数据迁移处理，不能作为普通热更新。
- `LoadDistribution` 统计的是分区数，不代表真实 key 数、字节数、CPU 或 QPS。
- 使用副本接口前要明确它返回的是环上候选成员；健康池的主节点故障切换是另一层逻辑。
- 服务发现的一致性和节点列表传播由外部控制面负责。

## 8. 验证状态

当前工作区中，`gyro/gyro` 单元测试和 `consistent-go` 的包级测试可通过；完整 `gyro` 集成场景仍有 fake gRPC 与原生连接健康状态相关失败，不能据此宣称所有集成流程已通过。文档中的能力描述以源码接口和已有测试覆盖为准。
